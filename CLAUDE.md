# Rules for Claude

- Do NOT run `git commit` or `git push`. Never commit or push any code.
- Edit code manually with the Edit/Write tools. Do NOT use Python/sed/shell scripts to modify source files.
- Firestore structure lives in `lib/constants/firestore_constants.dart`. Never type a collection, subcollection or fixed document name as a string in a provider, service or screen; use `FirestoreCollections`, `FirestoreSubCollections`, `FirestoreDocs` or `FirestoreFields`. The same file documents the saved JSON of every document and a tree of which data sits under which collection. Whenever code adds, renames or removes a collection, document or field, update that file in the same change (the tree and the JSON). If access changes, also update `firestore.rules`; if a new query needs a composite index, update `firestore.indexes.json`.
- Every collection / subcollection document shown in the UI goes through a model class in `lib/models` (`fromJson` / `toJson`). Never keep a raw `Map<String, dynamic>` from a snapshot in a provider field the UI reads, and never pass one into a widget. Adding a field means updating the model, the saved-JSON documentation in `firestore_constants.dart`, and `firestore.rules` together.
- Do NOT call `setState`. State lives in Provider (`ChangeNotifier`) and widgets read it with `Consumer` / `Selector` / `context.select`: use `Selector` (or `context.select`) when only one or two fields matter or the widget tree is large, and `Consumer` for a simple section. Screen-local state (filters, toggles, form fields, loading flags) goes in a small `ChangeNotifier` scoped to that screen with `ChangeNotifierProvider`. A `StatefulWidget` is allowed only to own a lifecycle object (`TextEditingController`, `AnimationController`, `PageController`) and must still not call `setState`.
- Deploy Firestore changes with `firebase deploy --only firestore:rules --project workzen2025` (add `firestore:indexes` for indexes). Run it with `--dry-run` first. Only deploy when the user asks, since it changes production.
- UI sizing and text: every dimension (widths, heights, paddings, margins, radii, icon sizes) uses `flutter_screenutil` (`.w`, `.h`, `.r`, `.sp`); never a bare number except hairlines (`Border` width, `Divider(height: 1)`). Text styles come from `getTextTheme()` (`lib/constants/const_textstyle.dart`), adjusted with `copyWith` for colour or weight. Never write `TextStyle(...)` or a raw `fontSize:` in a widget (the only exception is the `pdf` package's `pw.TextStyle`).
- Buttons: use `ConstantButton` (`lib/constants/constant_button.dart`) for every action button instead of a bare `ElevatedButton` / `OutlinedButton` (it has `isLoading`, `isOutlined`, `icon`, `isFullWidth`). Colours come from `ConstColors`, never `Colors.green` / `Colors.red` and the like.
- Loading: use `AppLoadingIndicator` (`lib/constants/apploading_indicator.dart`, built on `flutter_spinkit`) for every spinner. Never use a bare `CircularProgressIndicator`. (Shimmer placeholders for lists stay as they are.)
- Dropdowns and pickers: use `ConstantDropdown` (`lib/constants/constant_dropdown.dart`) for every dropdown and `ConstantDatePicker` / `ConstantTimePicker` / `ConstantDateRangePicker` (`lib/constants/constant_date_time_picker.dart`) for every date, time and date range choice. Never call `showDatePicker` / `showTimePicker` / `showDateRangePicker` or build a bare `DropdownButton` / `DropdownButtonFormField` in a screen.
- Validation: form field validators live in `lib/utils/validators.dart` (`Validators.email`, `Validators.password`, `Validators.required('your name')`, `Validators.mobileNumber`, ...). Pass them to a field's `validator:`; never write the checks inline in a screen. Add a new rule to `Validators` when none fits.
- For user messages (success, error, warning) use `ConstantSnackbar` (`lib/constants/constant_snackbar.dart`): `ConstantSnackbar.showSuccess`, `ConstantSnackbar.showError`, or `ConstantSnackbar.show(title:, backgroundColor:)` for other colours. Do NOT use `ScaffoldMessenger.of(context).showSnackBar(SnackBar(...))` in new code.
